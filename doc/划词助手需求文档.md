# 划词助手（WordPick）需求文档

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 文档状态 | 待评审 |
| 目标平台 | macOS + Windows（跨平台，Linux 为后续可选目标） |

---

## 1. 项目概述

### 1.1 背景

现有划词工具（如豆包划词助手）体验好，但存在两个痛点：

1. **强绑定特定 App**：每次使用必须打开对应桌面客户端，划词工具只是其附属功能，启动重、占资源；
2. **模型不可选**：翻译、解释等核心能力由厂商固定模型提供，用户无法按场景、成本、速度自由选择模型。

### 1.2 项目目标

开发一个**极致轻量、系统级、模型可自由配置**的划词助手：

- 在任何应用中选中文本即弹出迷你工具条，点击功能后在选区旁打开 AI 悬浮对话框；
- 翻译、解释、追问等核心能力由用户自配的在线大模型驱动；
- 支持按场景选择不同模型（快任务用小模型省钱，重任务用大模型保质）；
- 通过 npm 全局安装 / npx 一键使用，也支持拉取源码本地构建运行。

### 1.3 成功标准

| 指标 | 目标 |
| --- | --- |
| 安装包体积 | macOS ≤ 15MB，Windows ≤ 12MB（Tauri 体系 WebView 方案可达） |
| 常驻内存 | ≤ 120MB（空闲时） |
| 工具条弹出延迟 | 选中文本后 ≤ 300ms 出现 |
| 首次翻译结果 | 点击功能后 ≤ 2.5s 出现首个 token（流式输出） |
| 支持场景 | 浏览器、代码编辑器（VSCode 等）、Office、终端（快捷键唤起模式） |

### 1.4 命名

开发代号 **WordPick**（可替换），npm 包名建议 `wordpick-cli` 或 `wordpick`。

## 2. 术语定义

| 术语 | 含义 |
| --- | --- |
| 划词 / 选区 | 用户通过鼠标拖动（或键盘 Shift 选择）选中的一段文本 |
| 悬浮工具条（Toolbar） | 选中文本后在选区下方/右上方弹出的小窗口，包含功能按钮 |
| 对话框（Panel） | 点击工具条功能后弹出的较大悬浮窗口，承载 AI 结果与对话输入 |
| 钉住（Pin） | 将对话框固定在屏幕最上层且不因失焦而关闭 |
| 提供方（Provider） | 模型供应商，如 Moonshot、DeepSeek、OpenAI、阿里云百炼 |
| 场景（Scenario） | 一次 AI 调用的用途分类，如 translate / explain / chat |

## 3. 功能需求

> 编号规则：FR-x.y。P0 = 必须实现（MVP），P1 = 重要，P2 = 增强。

### 3.1 全局划词捕获（FR-1）

**FR-1.1（P0）** 用户在任意应用（浏览器、文本编辑器、IDE、终端、Office 等）中用鼠标滑动选中文本后，悬浮工具条自动出现在选区下方（无下方空间时自动改为上方/右侧，始终保持在屏幕可视区内）。

**FR-1.2（P0）** 选区取消（点击空白处、选区变化为新选区、切换应用窗口）时，工具条隐藏。若已从工具条打开对话框，则对话框行为遵循 3.5 的钉住规则，不受选区取消影响。

**FR-1.3（P1）** 工具条触发策略可配置，两种模式：

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| `auto`（默认） | 通过系统辅助功能 API 监听选区变化 | 大多数原生/浏览器应用 |
| `shortcut` | 不自动弹出，按全局快捷键主动唤起并读取剪贴板 | 终端、远程桌面、auto 模式失效的应用、注重隐私或低干扰用户 |

**FR-1.4（P1）** 划词长度过滤：选中文本为空或仅空白字符、或长度超过可配置上限（默认 5000 字符）时不弹出工具条。上限可调，防止误选整篇文章时误触。

**FR-1.5（P2）** 应用黑名单：可配置在某些应用中不弹出（如密码管理器、游戏）。

### 3.2 悬浮工具条（FR-2）

**FR-2.1（P0）** 工具条包含功能按钮，MVP 至少包含：**翻译、解释、设置**；预留扩展位供后续功能（润色、总结、代码解释等）插拔。

**FR-2.2（P0）** 工具条为无边框、透明背景、圆角卡片样式的小窗口，不占用任务栏/ Dock，不在 Alt+Tab / Cmd+Tab 切换列表中出现。

**FR-2.3（P1）** 工具条功能按钮可在设置中自定义显示/隐藏与排序。

**FR-2.4（P2）** 工具条支持键盘操作：弹出后按数字键（1=翻译、2=解释…）或 Tab+Enter 触发，Esc 关闭。

### 3.3 翻译功能（FR-3）

**FR-3.1（P0）** 点击「翻译」后，在选区下方（或右侧，可配置，空间不足自动翻转）打开翻译对话框，自动调用 AI 完成翻译并**流式**展示结果。

**FR-3.2（P0）** 语言自动检测：根据所选文本自动检测源语言，并给出默认目标语言——检测为英文 → 目标默认中文；检测为中文 → 目标默认英文；其他语言 → 目标默认中文。检测逻辑可在前端本地完成（字符集启发式：CJK、阿拉伯文、日文假名、谚文、拉丁字母分布等），不消耗 API 调用。

**FR-3.3（P0）** 语言可手动切换。支持语言至少包含：**中文（简体）、英语、德语、法语、日语、阿拉伯语**，另提供韩语、俄语、西班牙语作为扩展项（P1）。

**FR-3.4（P0）** 对话框下方提供输入框，用户可继续追问（如「把刚才的翻译改得更正式」「解释这个词在这句话里的含义」）。追问时携带原文与首轮翻译的上下文。

**FR-3.5（P1）** 翻译对话框提供「复制译文」「朗读原文/译文」（调用系统 TTS 或浏览器 SpeechSynthesis）按钮。

### 3.4 解释功能与多轮对话（FR-4）

**FR-4.1（P0）** 点击「解释」后，打开解释对话框。AI 基于所选文本给出**清晰、结构化**的解释，要求：

- 判断文本类型（技术概念 / 代码 / 日常表达 / 专业术语 / 长难句等）并采用对应的解释策略；
- 技术概念：先一句话总结，再分点展开，必要时举例；
- 代码：解释意图、关键行、潜在坑；
- 长难句/外语：先直译，再拆解语法与逻辑；
- 输出使用 Markdown 渲染，支持代码高亮。

**FR-4.2（P0）** 对话框下方提供多轮追问输入框，不断对话以彻底吃透所选内容。每轮对话携带完整上下文（原文 + 历史对话）。

**FR-4.3（P1）** 会话管理：同一对话框内上下文随对话轮数增长自动压缩（保留原文与最近若干轮，更早轮次摘要化），防止超长上下文造成的费用与延迟上升。

**FR-4.4（P2）** 解释对话框提供「换个角度解释」「举例说明」「出几道练习题」等快捷追问 Chips。

### 3.5 对话框通用行为（FR-5）

**FR-5.1（P0）** 对话框提供**钉住按钮**：

- 默认非钉住状态：点击对话框以外任意位置，对话框消失；
- 钉住后：对话框置顶显示于所有窗口之上，点击外部不消失，可与其他应用并行操作；再次点击取消钉住。
- 钉住状态在视觉上有明确标识（图钉图标填充/描边切换）。

**FR-5.2（P0）** 对话框样式随功能区分：翻译对话框突出译文区 + 语言切换器；解释对话框突出正文排版 + 追问区；标题栏颜色/图标随功能变化。

**FR-5.3（P0）** 对话框可拖拽移动（按住标题栏）；位置始终约束在屏幕可视区内。

**FR-5.4（P0）** 流式输出渲染：结果逐字/逐段出现，期间显示停止按钮；出错时（网络失败、限流、Key 无效）展示友好错误与重试按钮，Key 无效时提供直达设置的入口。

**FR-5.5（P1）** 对话框支持手动调整大小（宽度拖拽），记忆用户对每种功能对话框的尺寸偏好。

**FR-5.6（P2）** 明暗主题跟随系统，可手动锁定。

### 3.6 设置（FR-6）

**FR-6.1（P0）** 通过工具条「设置」按钮或全局快捷键 / 系统托盘菜单打开设置窗口，包含以下配置项：

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| 提供方与模型 | 增删改提供方，配置各场景（翻译/解释）使用的模型 | 见 §5.5 |
| API Key | 各提供方的 Key | 无（必填后可用） |
| 触发模式 | auto / shortcut | auto |
| 全局快捷键 | 唤起工具条 / 打开设置 | 可配置，默认 Alt+Q / Alt+, |
| 弹窗位置 | 选区下方 / 右上方 | 下方 |
| 划词长度上限 | 字符数 | 5000 |
| 应用黑名单 | 不弹出的应用列表 | 空 |
| 主题 | 跟随系统 / 明 / 暗 | 跟随系统 |

**FR-6.2（P0）** 项目内置一份**默认配置文件**（随仓库分发），包含所有配置项的默认值与注释说明；用户首次运行时在用户目录生成 `config.toml`（或 JSON），此后设置界面的修改与配置文件双向同步，方便偏好手动编辑配置文件的高级用户。

**FR-6.3（P0）** API Key 的存储安全：

- 优先存入系统安全存储：macOS Keychain / Windows Credential Manager（通过 Rust `keyring` crate）；
- 配置文件中的 `api_key` 字段支持明文（本地自用）与环境变量占位符（如 `"${DEEPSEEK_API_KEY}"`）两种形式；
- 应用内任何界面、日志、错误上报均不回显完整 Key（仅显示后 4 位）。

**FR-6.4（P1）** 首次启动引导（Onboarding）：检测无可用 Key 时，弹出简洁引导页说明如何获取 DeepSeek / Kimi 等的 Key 并粘贴，完成后即可用。

**FR-6.5（P1）** 设置中提供「连接测试」按钮：向所选模型发起最小请求，验证 Key 与网络连通性。

### 3.7 安装与启动（FR-7）

**FR-7.1（P0）** 支持三种使用方式：

| 方式 | 命令 | 说明 |
| --- | --- | --- |
| npm 全局安装 | `npm install -g wordpick` → `wordpick run` | 安装时按平台下载对应二进制（GitHub Releases），bin 入口启动后台常驻进程 |
| npx 使用 | `npx wordpick run` | 无需显式安装，直接运行 |
| 源码运行 | `git clone … && pnpm i && pnpm tauri dev` | 开发者模式 |

**FR-7.2（P0）** 启动命令支持子命令：`wordpick run`（启动/若已运行则唤起）、`wordpick settings`（打开设置）、`wordpick stop`（退出后台进程）、`wordpick status`（查看运行状态与版本）。

**FR-7.3（P0）** 单实例运行：重复启动不新开进程，仅唤起已有实例。

**FR-7.4（P1）** 开机自启开关（设置中可配），macOS 走 Login Items，Windows 走注册表 Run 键。

**FR-7.5（P2）** 系统托盘菜单：显示/隐藏、设置、开机自启、退出。

### 3.8 非目标（Out of Scope）

- 本地模型推理（如 Ollama 接入）——后续版本再议；
- 划词 OCR（图片/截图中的文字识别）；
- 团队协作、账号体系、云端同步；
- 浏览器插件形态（系统级应用已覆盖浏览器场景）。

## 4. 非功能需求

### 4.1 性能与资源

- **启动速度**：冷启动 ≤ 1.5s（后台常驻模式下，工具条弹出不受应用启动影响）；
- **常驻开销**：空闲 CPU ≈ 0%，内存 ≤ 120MB；选区监听采用事件驱动而非轮询；
- **窗口性能**：工具条与对话框均为无装饰透明窗口，创建开销需 < 100ms，采用窗口复用池（预创建、隐藏/显示切换）而非每次新建。

### 4.2 安全性与隐私

- API Key 存储遵循 FR-6.3；网络请求仅发往用户配置的提供方 Base URL，不内置任何上报/遥测端点；
- 开源（MIT/Apache-2.0），构建产物可复现，用户可以审计全部网络行为。

### 4.3 可靠性

- API 调用具备指数退避重试（网络类错误最多 2 次）；429 限流时明确提示；
- 对话框流式输出中断时保留已输出内容并提示可重试；
- 模型/提供方配置损坏时回退到默认配置并备份损坏文件。

### 4.4 兼容性

- macOS 13+（Ventura 及以上），Apple Silicon 与 Intel 双架构；
- Windows 10 1809+（WebView2 Runtime，安装包引导自动检测/安装）；
- 辅助功能权限缺失（macOS）时降级为快捷键唤起模式，并引导用户授权。

### 4.5 可维护性

- 系统能力层（Rust）与 UI 层（WebView）通过 Tauri command / event 解耦，UI 层不直接接触 OS API，便于替换 UI 技术栈；
- 模型适配层对 UI 暴露统一接口（见 §5.5），新增提供方仅需实现一个适配器。

## 5. 技术方案

### 5.1 技术选型

**桌面框架：Tauri 2.x（选定）**

| 维度 | Tauri 2.x ✅ | Electron |
| --- | --- | --- |
| 安装包体积 | ~5–15MB | ~80–150MB |
| 空闲内存 | 30–80MB | 150–300MB |
| 划词/快捷键/窗口控制 | Rust 原生能力强 | 依赖 node 库，均须各自打包 |
| 跨平台 | 官方支持 macOS/Windows/Linux | 同 |
| 前端技术栈 | 任意（产物为静态文件） | 任意 |
| 风险 | WebView 渲染差异需少量适配 | 体积与内存违背「极致轻量」目标 |

本项目用户明确要求极致便携轻量化，且系统级能力（辅助功能 API、全局快捷键、无边框置顶窗口、剪贴板监听）正是 Tauri/Rust 的强项，故选定 **Tauri 2.x**。

**前端技术栈：Vue 3 + TypeScript + Vite + Tailwind CSS + shadcn-vue（选定）**
理由：维护者最熟悉 Vue 3 生态，组合式 API 与 Pinia 足以胜任工具条/对话框/设置页这类多窗口独立挂载的轻量 UI；组件层选用 shadcn-vue（或 Naive UI，按需取舍），样式层统一 Tailwind。Markdown 渲染使用 `markdown-it` + `shiki`，流式渲染采用「追加增量解析」策略避免重复解析整篇文档。

**关键 Rust crate 选型：**

| 用途 | crate |
| --- | --- |
| 全局快捷键 | `global-hotkey`（tauri 插件亦可） |
| 剪贴板读取（快捷键唤起时） | `arboard` 或 tauri-plugin-clipboard |
| macOS 选区捕获 | `accessibility-sys` / `core-foundation`（直接调 AX API） |
| Windows 选区捕获 | `windows-rs`（UI Automation / GetGUIThreadInfo） |
| API Key 安全存储 | `keyring` |
| 配置 | `figment` 或 `config-rs`（TOML） |
| HTTP / SSE 流式请求 | `reqwest`（rustls，stream 特性） |
| 单实例与进程管理 | `single-instance`（tauri plugin） |
| npm 二进制分发 | `bin-wrapper` 或自研 postinstall 脚本 |

### 5.3 核心难点：选区检测与定位（划词功能的成败关键）

工具条必须知道两件事：**选中了什么文本**、**选区在屏幕的什么位置**。不同平台、不同应用的实现能力差异大，这是本项目最大的技术风险点，方案如下：

**macOS — 辅助功能（Accessibility）API 通道**

1. 监听系统焦点应用变化与选区变化事件（`AXFocusedUIElementChanged` / `AXSelectedTextChanged`）；
2. 从焦点元素读取 `AXSelectedText`（选中文本）与 `AXSelectedTextRange`；
3. 通过 `AXBoundsForRange` 获取选区末端的屏幕坐标（`CGRect`），工具条定位于该坐标下方；
4. 需要用户在系统设置中授予「辅助功能」权限，首次运行引导授权；未授权时降级为快捷键唤起模式并显著提示。

**Windows — UI Automation / GetGUIThreadInfo 通道**

1. 通过 `GetGUIThreadInfo` 获取前景线程的 caret/选区矩形（对大多数标准控件有效）；
2. 对支持 UIA `TextPattern` 的应用（Edge、Chrome、Office、记事本等主流应用均支持）读取 `TextPattern.GetSelection()` 与 `GetBoundingRectangles` 精确定位；
3. 兜底：取光标位置（`GetCursorPos`）+ 焦点窗口位置估算；
4. 无需用户授权（Windows 无辅助功能授权门槛，但 UIA 在个别自绘应用如部分终端中拿不到选区）。

**终端等特殊应用 — 快捷键唤起通道（兜底，可配置）**

终端（Terminal.app / iTerm2 / Windows Terminal）大多不向 AX/UIA 暴露选区文本，方案：

- 用户选中文本后按全局快捷键（默认 Alt+Q），应用读取剪贴板内容并于光标处弹出工具条；
- 可选「读取后还原剪贴板」（弹出后恢复原内容，不污染用户剪贴板）。

**统一抽象：** Rust 层定义 `SelectionProvider` trait：

```rust
trait SelectionProvider {
    fn watch(&self, cb: impl Fn(SelectionEvent) + Send);   // 事件驱动
    fn current_selection(&self) -> Option<Selection>;      // 主动读取
}

struct Selection {
    text: String,
    /// 选区末端的屏幕坐标（逻辑像素，多显示器感知）
    anchor: Option<(i32, i32)>,
    /// 来源：Ax / Uia / Shortcut（快捷键路径经剪贴板读取）
    source: SelectionSource,
}
```

两个自动探测实现（AxSelectionProvider / UiaSelectionProvider）按平台与权限组合；快捷键路径复用剪贴板读取能力（arboard），不独立成 Provider。UI 层完全不感知差异。**选区坐标准确性定义为「尽力而为」**：拿到坐标则精确定位，拿不到则以光标位置定位——这一约定也写入了验收标准。

### 5.4 窗口模型

Tauri 中创建 3 类窗口，均为 `decorations: false, transparent: true, skipTaskbar: true, resizable: 按类型`：

| 窗口 | 特性 | 生命周期 |
| --- | --- | --- |
| 工具条（toolbar） | 无焦点抢占（`focus: false`）、非置顶，尺寸 ≈ 内容自适应 | 单实例复用，跟随选区显示/隐藏 |
| 对话框（panel） | 可聚焦、可拖拽、钉住时 `alwaysOnTop: true`，尺寸 420×540 起（可记忆） | 功能会话制：点击工具条功能时携带 (selection, scenario) 创建或复用 |
| 设置（settings） | 标准有焦点的普通窗口 | 单实例，重复打开聚焦已有窗口 |

**弹窗定位算法：** 以选区锚点计算首选位置（选区下方 8px 处，水平居中对齐选区）；若超出当前显示器工作区（扣除 Dock/任务栏），依次尝试：上方 → 右侧 → 左侧；仍不可行则以锚点为左上角展开。显示器边界与多显示器（DPI 缩放）通过 Rust 层获取显示器信息统一处理。

**钉住实现：** 钉住 = `setAlwaysOnTop(true)` + 焦点策略切为「永不因外部点击失焦关闭」；非钉住 = 监听窗口 blur 事件自动隐藏销毁。该状态在标题栏按钮上即时反馈。

### 5.5 AI 模型接入方案

**统一适配层（OpenAI 兼容协议为核心）**

Moonshot（Kimi）、DeepSeek、阿里云百炼（Qwen）、OpenAI 四家均提供 OpenAI 兼容的 Chat Completions 接口（Moonshot / DeepSeek / 百炼为完整兼容，OpenAI 为原生协议），因此适配层以 OpenAI SDK 协议为基准抽象：

```ts
interface ModelAdapter {
  /** 场景化对话，SSE 流式返回 */
  chat(params: ChatParams): AsyncIterable<ChatChunk>;
  /** 最小化连通性测试（FR-6.5） */
  testConnection(): Promise<ConnectionTestResult>;
}

interface ChatParams {
  scenario: 'translate' | 'explain' | 'chat';
  systemPrompt: string;        // 按场景注入，见下
  history: ChatMessage[];      // 含原文上下文与对话历史
  stream: true;
  temperature?: number;
}
```

- Rust 层持有 reqwest 流式请求，向 WebView 透传 SSE chunk（Tauri event），UI 逐段渲染；
- 提供方配置仅需三项：`base_url`、`api_key`、`model`，即可接入任意兼容服务（天然支持 OneAPI / OpenRouter 等聚合网关）；
- 新增官方提供方 = 内置一份默认配置模板 + 域名白名单提示，无需改代码。

**场景化模型选择（按 能力 / 速度 / 价格 三角权衡）**

高频场景（翻译、短文本解释）优先「快+便宜」，低频重场景（复杂代码、长文深挖）可用更强模型。默认值基于 2026 年 9 月公开定价（来源见文末）：

| 场景 | 首选（默认） | 备选 | 理由 |
| --- | --- | --- | --- |
| 翻译 | DeepSeek V4 Flash（输入 $0.14 / 输出 $0.28 每百万 token） | Qwen3.7-Flash（约 $0.03–0.07 / $0.13–0.20） | 翻译是最高频调用，Flash 级模型速度最快、成本可忽略；质量足够 |
| 解释/多轮对话 | DeepSeek V4 Pro（$0.435 / $0.87） | Kimi K2.6（$0.95 / $0.4→4.0）、Qwen3.7-Plus（$0.48 / $1.92） | 解释质量取决于模型本体能力，Pro 级性价比最优；追求解释深度可一键切 Kimi K2.6（256K 长上下文） |
| 兜底/尝鲜 | Qwen3.7-Flash | — | 极低价格 + 阿里云免费额度，适合新用户体验 |

OpenAI（GPT-5.6 系列，$5 / $30 每百万 token）作为高端可选提供方内置，但不作默认推荐——对本工具的高频短文本场景性价比偏低。

**系统提示词（System Prompt）按场景内置模板化**，示例（翻译场景）：

```javascript
你是翻译引擎。将用户给出的文本从 {source_lang} 翻译为 {target_lang}。
要求：1) 只输出译文，不要解释；2) 保留原文格式（换行、列表、代码块）；
3) 专业术语使用目标语言行业标准译法；4) 文本过短时给出 2 个语义的候选译法。
```

解释场景模板则要求「先一句话总结，再结构化分点，必要时举例，输出 Markdown」。

**成本控制设计：** 对话历史压缩（FR-4.3）；翻译请求 `max_tokens` 上限；连续追问超过可配置轮数（默认 10 轮）时提示用户是否开新会话；设置页展示各提供方本月预估消耗（按本地 token 计数估算）。

### 5.6 配置系统

```javascript
~/.config/wordpick/config.toml          # macOS: ~/Library/Application Support/wordpick/
                                        # Windows: %APPDATA%\wordpick\config.toml
```

```toml
# WordPick 用户配置（首次运行自动生成，全部可缺省——缺省值即内置默认）
general = { trigger_mode = "auto", popup_position = "below", max_selection_chars = 5000,
            blacklist_apps = [], theme = "system",
            shortcut_toggle = "Alt+Q", shortcut_settings = "Alt+," }

[[providers]]
name = "deepseek"
base_url = "https://api.deepseek.com/v1"
api_key = "${DEEPSEEK_API_KEY}"   # 支持环境变量占位符或明文
default_model = "deepseek-v4-flash"

[[providers]]
name = "moonshot"
base_url = "https://api.moonshot.cn/v1"
api_key = "${MOONSHOT_API_KEY}"
default_model = "kimi-k2.6"

[scenario_models]
translate = { provider = "deepseek", model = "deepseek-v4-flash" }
explain   = { provider = "deepseek", model = "deepseek-v4-pro" }
```

- 读取优先级：环境变量 > 用户配置文件 > 内置默认；
- API Key 若配置为 `"${ENV_VAR}"` 形式，运行时从进程环境解析（呼应用户此前「Windows 中将 token 存环境变量、配置中不保存明文」的诉求）；
- keychain 中的 Key 优先于配置文件（设置界面保存时写入 keychain）。

### 5.7 关键时序（翻译为例）

```javascript
用户拖选文本
  → Rust 选区探测器捕获 SelectionEvent(text, anchor)
  → 窗口管理器定位并在 anchor 下方显示工具条（复用窗口，<100ms）
用户点击「翻译」
  → UI 请求 Rust 创建 Panel 窗口（携带 selection + scenario=translate）
  → UI 本地启发式检测语言 → 确定 (source, target)
  → Rust 模型适配层按 scenario_models 选择提供方，组装 system prompt + 原文
  → reqwest 发起 SSE 流式请求
  → chunk 经 Tauri event 推送至 Panel，Vue 增量渲染译文
用户继续追问
  → UI 将追问 + 历史一并提交，同一 Panel 内续流
```

### 5.9 npm 分发实现要点

参考 esbuild / Biome 的成熟模式：

1. npm 包 `wordpick` 本体仅含 JS 引导脚本（~几十 KB）与 postinstall 脚本；
2. postinstall 依据 `process.platform` + `process.arch` 从 GitHub Releases 下载对应二进制（`wordpick-darwin-arm64`、`wordpick-win32-x64` 等），缓存于包目录；亦可选配镜像源环境变量 `WORDPICK_BINARY_MIRROR`（国内加速）；
3. bin 入口的 JS 脚本 exec 对应二进制；`npx wordpick run` 走同一逻辑；
4. CI（GitHub Actions）按 tag 构建 Tauri 产物并发布 Release，同时发布 npm 包，版本号联动。

### 8.1 语言检测的本地启发式规则（FR-3.2 实现要点）

- 存在阿拉伯文字符（\u0600-\u06FF）→ 阿拉伯语；
- 存在谚文字符 → 韩语；存在西里尔字符 → 俄语；
- 存在平/片假名 → 日语；存在 CJK 统一表意文字 → 中文（简/繁按字符分布粗判，不影响翻译目标）；
- 否则 → 拉丁语系（英/德/法/西按高频词与变音符粗判，默认按英语处理，用户可手动切换）；
- 检测结果在对话框语言切换器中高亮展示，用户一键可改。
